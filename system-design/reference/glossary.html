System Design · Reference

Glossary

The shared vocabulary of the course. Every lesson uses these terms exactly as defined here. Grows as we go.

Terms are grouped loosely by theme. Anchor examples come from the systems you're curious about: YouTube/Netflix/Spotify and Twitter/WhatsApp/Discord.

The request path

Client — The program that asks for something: your phone's YouTube app, a browser tab, the Discord desktop app. It initiates requests and shows you the result.

Server — A program (running on a computer somewhere) that listens for requests and sends back responses. "A server" can mean the software or the machine it runs on.

Client–server model — The basic shape of almost every app you use: many clients send requests to one or more servers, which do work and reply. Lesson 1.

Request / Response — One round trip. The client sends a request ("give me my feed"); the server sends back a response (the feed data). Most web communication is this back-and-forth.

IP address — The numeric "postal address" of a machine on a network (e.g. 142.250.72.14). Requests need one to know where to go.

DNS (Domain Name System) — The internet's phone book. Translates a human name like youtube.com into the IP address of a server. Your client does a DNS lookup before it can send a request.

Latency — How long one round trip takes (e.g. 80 ms). Low latency = feels instant. This is why where a server physically sits matters.

Throughput — How many requests a system handles per unit time (e.g. 50,000 requests/second). Latency is speed of one; throughput is volume of many.

API (Application Programming Interface) — The defined set of requests a server agrees to answer ("here are the questions you may ask me, and the shape of the answers"). The contract between client and server.

Video delivery

Segment — A small chunk of a video, typically a few seconds long, stored as its own file. Video is never delivered as one big download; it's delivered as a run of segments fetched back to back. Lesson 2.

Manifest (or playlist) — A text file listing a video's segments in order. The client fetches it first to learn what to request. In HLS it's an .m3u8 file.

VOD (Video on Demand) — Stored video: every segment exists before anyone presses play. Its manifest is final and never changes, so the client fetches it once and can seek anywhere.

Live edge — The newest available segment of a live stream: the boundary of what exists. Players deliberately sit a few segments behind it, trading freshness for a buffer that absorbs network wobble.

Pre-positioning — Copying content to caches near viewers before they ask for it (Netflix fills its appliances nightly). Only possible for stored video — you cannot pre-position bytes that don't exist yet.

Request collapsing (coalescing) — Merging many simultaneous requests for the same uncached object into a single fetch to the origin, then serving all of them from that one response. What makes a live stream's synchronised stampede affordable.

Thundering herd — A crowd of requests hitting one uncached resource at the same instant. Live video causes this by nature: every new segment is born cold and wanted immediately by everyone.

Scaling out

Load balancer — A machine that sits in front of many servers and decides which one handles each request. DNS points at it, not at your servers, so the whole fleet hides behind one address. Spreads load and routes around dead servers. Lesson 3.

Horizontal scaling — Handling more load by adding more machines (rather than a bigger one, which is vertical scaling). Cheaper at scale, but only works if the machines are interchangeable.

Interchangeability — The property that any server can answer any request. What a load balancer requires, and what state destroys. Nearly every design rule in this course exists to protect it.

State — Anything a server remembers between requests (your login, your cart). State kept in one server's memory is invisible to the others, which is why it breaks horizontal scaling. The central question of system design is where state is allowed to live.

Stateless — A server that keeps nothing of its own between requests; everything it needs comes with the request or from a shared store. Stateless servers are interchangeable, disposable, and survivable.

Sticky session (session affinity) — Pinning a user to one server so their in-memory state stays valid (e.g. NGINX's ip-hash). Doesn't make an app stateless — it hides statefulness behind routing. Costs: lumpy load, and sessions die with the machine.

Health check — The load balancer periodically polling servers to see who's alive, pulling failures out of rotation. How a fleet survives one machine dying.

Single point of failure (SPOF) — Any component whose death kills the system. A lone load balancer is one — which is why real deployments run several (active-passive or active-active).

Layer 4 / Layer 7 — How deeply a balancer looks. L4 sees only IPs and ports (fast, blind). L7 reads the actual HTTP request — headers, cookies, path — so it can route on content (flexible, costlier).
