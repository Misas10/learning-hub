System Design · Lesson 3

One Server Becomes Many

Promised in Lesson 1, deferred twice, finally here. The load balancer looks like a traffic cop — a box that spreads requests around. It isn't. Its real job is to tell you a hard truth about where your data is allowed to live.

Why this, now? You've had one server since Lesson 1, and one server serves nobody at YouTube scale. This is the lesson where your architecture stops being a diagram and starts being a system — and it hands you the question that the rest of the course is really about.

The problem, restated from Lesson 1

Lesson 1 ended on a cliffhanger: one server would melt under a billion requests. So: buy more servers. Easy.

Except you immediately hit a wall you already know about. Your client does a DNS lookup for youtube.com and gets back an IP address — one number, one machine. That's the whole mechanism from Lesson 1. So how do ten thousand servers hide behind one address?

Answer: DNS doesn't point at your servers at all. It points at one machine standing in front of them — the load balancer. Your request goes there first, and it decides which server actually does the work.1

Notice what didn't change. The client still resolves a name, still sends the same request, still waits. Scaling is invisible from the outside. That's the trick — and it's the same move you saw in Lesson 2, where live and stored video used the identical request shape.

The one fact that changes everything

The whole lesson, in one line. The moment a load balancer exists, you no longer control which server handles your request — so every server must be able to answer any request. The servers must be interchangeable.

That's the root fact. It sounds administrative. It is actually a brutal constraint, and everything below falls out of it.

NGINX is blunt about the reality: "each subsequent client's request can be potentially distributed to a different server. There is no guarantee that the same client will be always directed to the same server."2 Request #1 hits server 2. Request #2 hits server 7. Nobody asked your permission.

Consequence 1: your server is not allowed to remember you

Here's where it bites. Say a user logs in. Request #1 lands on server 2, which stores "this user is logged in" in its own memory. Request #2 lands on server 7.

Server 7 has never heard of them. Logged out. Cart empty.

The server did nothing wrong — it remembered something. But memory is what makes servers non-interchangeable. Anything a server keeps in its own memory is a fact the other servers don't have, and the load balancer will happily route around it. This is state, and it's the villain of this lesson.

Sticky sessions are real and widely used — NGINX ships ip-hash precisely so "requests from the same client will always be directed to the same server."2 But look at what you gave up: you re-broke interchangeability on purpose. Your load is now lumpy, and one dead machine logs a chunk of users out.

This is the question the whole course is really about. "Move the state out" — out where? Some box that every server can reach, that's fast, that must never lose your data, and that now has all your servers hammering it. You just invented the database and the cache, and you invented them by necessity rather than by being told they exist. Every remaining lesson is, in some form, about where state lives and what that costs.

Consequence 2: the free win — it routes around the dead

Interchangeability has a gift attached. If any server can answer any request, then a server dying is survivable: send its requests to the others.

The load balancer finds out who's alive with health checks — polling each server, taking failures out of rotation. So the primer lists "preventing requests from going to unhealthy servers" alongside spreading load.1

This is worth pausing on, because the name lies to you. "Load balancer" sounds like it's about load. But the same box is also how your system survives a machine catching fire at 3am. Availability isn't a separate feature you bolt on later — you got it for free the moment you made servers interchangeable. That's why statelessness is worth the pain.

Consequence 3: you just built a single point of failure

Look at the diagram again. Every request in your entire system now goes through one box.

You added servers so that no single machine could take you down — and then you put a single machine in front of all of them. The primer says it plainly: a lone load balancer "is a single point of failure," and fixing it means "multiple load balancers" in active-passive or active-active setups, "further increasing complexity."1 It can also become a bottleneck in its own right.1

So: who load balances the load balancer? Google's answer starts one layer earlier — DNS itself, returning several addresses so clients spread across multiple entry points, though they note DNS is a coarse instrument because caching and TTLs limit how fast you can change anything.3

The pattern to notice. Three lessons, three times: you solved a problem and the solution created the next problem. That's not you doing it wrong — that's the actual texture of the field. Nobody reaches a design with no problems left; you reach one whose problems you chose on purpose.

How it picks (briefly)

Two knobs worth knowing, and no more than that for now.

Which server? NGINX's default is round-robin: "requests to the application servers are distributed in a round-robin fashion."2 Fine — if requests are uniform. They rarely are. Least-connected instead sends "the next request to the server with the least number of active connections," which NGINX says "allows controlling the load on application instances more fairly in a situation when some of the requests take longer to complete."2

A source-quality note, since it's a live lesson from last session: a blog I found while researching this claimed least-connections is "the best default for most web applications." NGINX — who wrote the thing — say round-robin is the default and least-connected is better when request durations vary. Not the same claim. When a vendor's docs and a listicle disagree, believe the vendor. That's a live example of the streaming problem from Lesson 2's research, which is why every claim here is quoted from someone who implements or operates it.

How deeply does it look? A layer 4 balancer sees only IPs and ports — it forwards traffic without reading it. A layer 7 balancer reads the actual HTTP request (headers, cookies, path), so it can route on content: send /video/* to the video fleet, billing to hardened machines. The primer states the tradeoff exactly: "At the cost of flexibility, layer 4 load balancing requires less time and computing resources than Layer 7, although the performance impact can be minimal on modern commodity hardware."1 Cheap and blind, or smart and costly.

Recall before you check

Answer out loud first — badly, if necessary. Retrieving it wrong then seeing it beats reading it smoothly.

Rebuild the lesson from the root fact: "you don't control which server gets your request." What follows? Servers must be interchangeable → so a server must not keep anything in its own memory (state breaks interchangeability) → so either pin users to servers (sticky sessions, lumpy load, sessions die with the machine) or move state to a shared store (hello, database/cache) → and because any server can serve anyone, a dead server is survivable, which is where health checks and availability come from → but the balancer itself is now a single point of failure. If you can walk that chain, you have the lesson.
From Lesson 1: what does DNS actually return now that there are ten thousand servers? The load balancer's address — not a server's. The client's experience is exactly Lesson 1: one name, one IP, one request, waiting on latency. The entire fleet is invisible from outside. (Google's frontend layer complicates this — DNS can hand back several addresses to spread clients across entry points.3)
Interleave with Lesson 2: Netflix pre-positions films in caches near you. Does that box need to be stateless too? Worth thinking about rather than answering fast. A cache is deliberately full of state — but it's state that's identical everywhere and losable. If an pre-filled cache dies, you refetch from origin; nothing is destroyed. Your login session in server 2's RAM is the opposite: unique to that machine, and gone forever if it dies. That's the distinction that matters — not "state or no state" but can this state be rebuilt from somewhere else?

Primary source — read next The System Design Primer — "Load balancer" (Donne Martin). Short, free, and the canonical map: L4 vs L7, the algorithms, and — unusually honest for an intro — an explicit disadvantages list. Read that disadvantages section slowly; it's the part most tutorials skip.

Then, if you want the real thing: Google's SRE book, "Load Balancing at the Frontend" — free online, written by the people running it at planetary scale. It'll show you how much the tidy diagram above is hiding. Harder than the primer; skim it and let it be humbling rather than fully understood.

Two candidates, both already teased — the database (the box that must never lose your data, now with every server hammering it) or the CDN (still owed from Lesson 2, and the centre of gravity for your streaming anchor).
