System Design · Lesson 1

The Request's Journey

Before we design anything big, we need the atom that every big system is built from: one request, from your phone to a server and back.

Why this, first? Your mission is to open the hood on YouTube, Netflix, Twitter and WhatsApp and actually understand them. Every one of those — no exceptions — is millions of copies of the single round trip you'll learn here. Master the atom and the molecules get easy.

The whole internet, in one shape

Almost every app you use has the same basic shape: a client asks, a server answers. This is the client–server model.

  • The client is the program that wants something — the YouTube app on your phone, a browser tab, the Discord window on your laptop.
  • The server is a program running on a computer in a data centre that listens for requests and sends back answers.

The client never has the data itself. When you open Twitter, your phone is nearly empty of tweets — it has to go ask a server: "what's in my feed?" That ask-and-answer is a request and response.1

The four steps:

  1. Find the server. The client only knows the name youtube.com, not where it lives. It asks DNS — the internet's phone book — which returns an IP address, the numeric location of a machine.
  2. Get the address back. Now the client knows where to send its request.
  3. Send the request. The client sends a message to that address: "give me video #abc123." What it's allowed to ask for is defined by the server's API — the menu of questions the server agrees to answer.
  4. Get the response. The server does its work (finds the video) and sends the data back. Your app plays it.

That entire round trip has a duration — its latency. When something "feels instant," latency was low (tens of milliseconds). When the spinner spins, it wasn't. Almost everything in system design is, ultimately, a fight to keep latency low while serving enormous throughput (many requests at once).

Naming trap: "server" means both the software that listens and the machine it runs on — people use it both ways. One physical machine can run many server programs; one server program can run across many machines. We'll untangle this in Lesson 2.

Recall before you check

Retrieval — pulling an answer from memory before seeing it — is what makes knowledge stick. Try each before you open it.

Why can't your phone just show your Twitter feed without talking to a server? Because the client holds almost no data of its own. The tweets live on Twitter's servers; your phone must send a request and wait for the response before it has anything to show. The client asks; the server answers.
What job does DNS do, and why is it needed before any request? DNS translates a human-friendly name (youtube.com) into the numeric IP address of a machine. A request can't be sent until the client knows where to send it — so the DNS lookup happens first.
What's the difference between latency and throughput? Latency = how long one round trip takes (speed). Throughput = how many requests are handled per second (volume). A system can have low latency but low throughput, or vice versa — they're different problems.
