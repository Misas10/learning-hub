System Design · Lesson 2

Live vs Stored Video

You asked how the request changes when the video is live instead of stored. The answer is delightful: the request barely changes at all. One small fact changes — and everything else follows from it.

Why this, now? You asked the question at the end of Lesson 1, so we're taking the detour. It's a good one: it takes the single round trip you already know and shows you how to derive an architecture from one constraint, instead of memorising two. That derivation move is the core skill of system design.

First: video isn't one big download

The instinct is that pressing play downloads a video file. It doesn't. Video is chopped into segments — small files, typically a few seconds each — plus a manifest: a text file listing the segments in order.1

So playback is not one exotic request. It's the ordinary request from Lesson 1, on repeat:

  1. GET the manifest → "here are the segments."
  2. GET segment 1, GET segment 2, GET segment 3… → play them back to back.

This is true for a 2011 YouTube upload and for a live World Cup final. Same protocol, same plain HTTP requests, same shape you already learned. Hold onto that — it's why the comparison below is fair.

The one fact that changes

The whole lesson, in one line. For stored video, every segment already exists. For live video, the segment you want next has not been created yet. Nobody has kicked the ball.

That's it. That's the only real difference. Everything below is a consequence — and the useful exercise is to derive each one yourself before you read it.

Consequence 1: the manifest stops holding still

For stored video, the manifest is complete and final. The spec is blunt about it: a playlist marked VOD "MUST NOT change."1 It ends with a tag literally called EXT-X-ENDLIST — that's all of them, there will be no more. Fetch it once and you're done forever.

A live manifest has no EXT-X-ENDLIST, because the story isn't over. And that absence obliges the server to keep writing: it "MUST make a new version of the Playlist file available that contains at least one new Media Segment."1 So the client "MUST periodically reload" it.1

This creates a request that has no equivalent in stored video: the poll. A live player sits in a loop asking "anything new? anything new? anything new?" — forever, for as long as you watch.

Consequence 2: you cannot buffer the future

Notice what the diagram takes away from you. With a stored film you can jump to minute 47, and you can grab segments far ahead of playback — a deep buffer, which is your armour against a wobbly network. If your wifi drops for 20 seconds, you had 60 seconds banked, and you never notice.

Live has no future to fetch. The newest segment is the edge of reality — this is the live edge. You cannot bank 60 seconds ahead of a match that hasn't been played.

So a live player deliberately hangs back from the edge. The spec advises the client "SHOULD NOT choose a segment that starts less than three target durations from the end of the Playlist file," because "doing so can trigger playback stalls."1 That's the trade in its rawest form: every second of safety buffer is a second of being behind live. It's why your stream shows the goal after you hear next door cheer.

This is the shape of the whole field. Nobody "solved" this — they chose. Buffer more (safe, laggy) or buffer less (live, fragile). Lesson 1 said system design is a fight to keep latency low; here's the first time you can see what that fight actually costs.

Consequence 3: caching flips upside down

Here's the part that pays off most, and it's about time.

Stored video has a luxury: it exists long before anyone wants it. So you can put copies near people in advance. Netflix does exactly this — it "pre-fills" its cache machines "with the appropriate content for your geographical location," with "nightly content fill and updates."3 By the time you press play, the film may already be sitting in a box at your ISP. The request never travels far. Netflix's hard problem isn't speed — it's prediction: guessing which titles to ship where, before demand exists.

Live can't play that game at all. You cannot pre-position bytes that don't exist. The newest segment is, by definition, in nobody's cache the instant it's born. Every live segment starts cold. That sounds like a catastrophe — a million viewers, all missing the cache, all stampeding your origin server at once.

And now the twist:

The thing that makes live hard is the same thing that makes it easy. A million viewers all want the same segment at the same instant. That synchronisation is the stampede — but it's also the most perfect cache locality you will ever be handed.

Because the requests are identical, they can be merged. Fastly calls it request collapsing: "combining multiple requests for the same object into a single request to origin, and then potentially using the resulting response to satisfy all pending requests."2 The first request goes to the origin; everyone else waits in line for that one answer and is served from it.

So a mob all screaming for the same thing is the best possible mob. One fetch feeds all of them. Stored video never gets this gift: at any moment your viewers are scattered across thousands of titles and thousands of positions within them — every request a different object.

The comparison, assembled

Stored (on-demand)Live
The segmentsAll exist alreadyNewest one just born; next doesn't exist
Manifest requestsFetched once, never changesRe-fetched on a loop, forever
Seek / prefetchAnywhere; buffer as deep as you likeNo future to fetch; hang back from the edge
Cache stateWarm — pre-positioned before you askCold — always, unavoidably
Request patternScattered: many titles, many positionsConverged: everyone on one segment
The hard problemPrediction & storage: what to put whereTime: encode, ship, and stay near live

Which collapses to one sentence worth keeping:

Stored video buys speed with space — put copies everywhere, ahead of time.
Live video can't buy anything ahead of time — so it buys speed with sameness: one fetch, fanned out to millions.

Recall before you check

Answer out loud first. Retrieving it wrong and then seeing it beats reading it smoothly — that's the difficulty that makes it stick.

Without scrolling up: what is the single fact that all the differences come from? For stored video every segment already exists; for live, the next segment hasn't been created yet. Polling, no-seeking, cold caches, the lag behind live — all of it is downstream of that one fact. If you can rebuild the list from this sentence, you've got the lesson.
Why is a live player deliberately several seconds behind the live edge? Because the buffer is its only protection against network wobble, and live gives it nothing to buffer except the small gap it leaves. Sitting back ~three segments (per RFC 8216) trades freshness for stability. Sit right on the edge and you stall whenever a segment is late.
From Lesson 1: DNS runs before any request. Does that change for live vs stored? No — and that's the point worth noticing. The client still resolves a name to an IP, still sends requests, still waits on latency. Live doesn't add new machinery to the request path; it changes which requests get made, and when. New systems are usually the old atom, rearranged.
